# یادداشت‌های یادگیری Z — فاز ۱ (مطالعه مقدماتی)

مبانی زبان Z، راه‌اندازی ابزارها، و جمع‌بندی کارهای مشابه از دیدی که برای نوشتن مشخصات صوری به کار می‌آید.

---

## ۱. Z چیست و چرا از آن استفاده می‌کنیم؟

Z یک زبان مشخصه‌سازی صوری (formal specification) است، نه یک زبان برنامه‌نویسی. با Z شما **چیستی** رفتار سیستم را با عبارات ریاضی دقیق توصیف می‌کنید، نه **چگونگی** پیاده‌سازی آن را. مبنای Z سه چیز است:

- **نظریه مجموعه‌ها** — برای مدل کردن داده‌ها (مجموعه کاربران، مجموعه مقالات، و...)
- **منطق مرتبه اول** — برای بیان قیدها و قوانین (پیش‌شرط‌ها، پس‌شرط‌ها، ثابت‌های حالت)
- **حساب لامبدا (typed)** — هر عبارت در Z یک نوع مشخص دارد؛ همین موضوع باعث می‌شود بتوان مشخصات را قبل از هرگونه پیاده‌سازی از نظر سازگاری بررسی کرد (type-checking)

مزیت اصلی Z این است که قوانین حساسی مثل «هر مقاله حداقل ۲ داور دارد» یا «داور نباید مقاله خودش را داوری کند» را می‌توان به‌صورت گزاره‌های ریاضی نوشت و **قبل از نوشتن حتی یک خط کد**، درستی منطقی آن‌ها را بررسی یا اثبات کرد.

## ۲. مبانی ریاضی مورد نیاز

| نماد | معنی | مثال |
|---|---|---|
| `∈` | عضویت در مجموعه | `p ∈ Papers` |
| `⊆` | زیرمجموعه | `Accepted ⊆ Papers` |
| `ℙ X` | مجموعه توانی X (همه زیرمجموعه‌های ممکن) | `ℙ REVIEWER` |
| `X ↔ Y` | رابطه بین دو مجموعه | `authors : USER ↔ PAPER` |
| `X ⇸ Y` | تابع جزئی (partial function) — هر ورودی حداکثر یک خروجی دارد، اما لازم نیست همه ورودی‌ها پوشش داده شوند | `status : PAPER ⇸ PaperStatus` |
| `X → Y` | تابع کامل (total function) — همه ورودی‌ها باید پوشش داده شوند | |
| `dom f` / `ran f` | دامنه / برد یک رابطه یا تابع | `dom borrowed` |
| `∪ , ∩ , \` | اجتماع، اشتراک، تفاضل مجموعه‌ها | |
| `{x ↦ y}` | یک زوج مرتب (نگاشت x به y) در یک رابطه | |
| `⩤ , ⩥` | تفریق دامنه / برد (domain/range subtraction) — حذف زوج‌هایی که کلیدشان در یک مجموعه است | `{b} ⩤ borrowed` |
| `∀ , ∃` | برای همه / وجود دارد | `∀ p : Papers • ...` |

## ۳. نت‌گذاری طرحواره (Schema Notation)

هسته اصلی Z، **طرحواره (schema)** است: یک جعبه که در نیمه بالایی آن **اعلانات (declarations)** و در نیمه پایینی آن **قیدها (predicates)** نوشته می‌شود.

```
SchemaName
  variable1 : Type1
  variable2 : Type2
——————————————————————
  predicate1
  predicate2
```

### ۳.۱ طرحواره حالت (State Schema)
متغیرهای حالت کل سیستم و قیدهای همیشه‌برقرار (invariant) را نگه می‌دارد.

### ۳.۲ طرحواره اولیه (Init Schema)
وضعیت آغازین سیستم را مشخص می‌کند (معمولاً مجموعه‌ها خالی هستند).

### ۳.۳ Δ (Delta) و Ξ (Xi)
- `ΔState` یعنی «این عملیات ممکن است حالت سیستم را تغییر دهد» — به‌طور خودکار دو نسخه از متغیرهای حالت را وارد می‌کند: نسخه **قبل** (بدون علامت) و نسخه **بعد** (با آپاستروف `'`)
- `ΞState` یعنی «این عملیات حالت را تغییر نمی‌دهد» (مثلاً یک عملیات فقط-خواندنی مثل «مشاهده وضعیت مقاله»)

### ۳.۴ ورودی (`?`) و خروجی (`!`)
هر متغیری که با `?` تمام شود ورودی عملیات است (چیزی که کاربر می‌دهد) و هر متغیری که با `!` تمام شود خروجی است (چیزی که سیستم برمی‌گرداند).

### ۳.۵ حالت قبل/بعد
در بخش قیدها، نام بدون آپاستروف = مقدار **قبل** از عملیات، نام با آپاستروف (`'`) = مقدار **بعد** از عملیات. پس‌شرط‌ها معمولاً رابطه بین این دو را بیان می‌کنند.

## ۴. یک مثال: سامانه ساده امانت کتاب

**مجموعه‌های پایه:**
```
[MEMBER, BOOK]
```

**طرحواره حالت:**
```
LibrarySystem
  stock    : ℙ BOOK          -- همه کتاب‌های موجود در کتابخانه
  borrowed : BOOK ⇸ MEMBER   -- کتاب‌های امانت‌رفته و امانت‌گیرنده هرکدام
——————————————————————
  dom borrowed ⊆ stock       -- فقط کتاب‌های موجود قابل امانت‌اند
```

**طرحواره اولیه:**
```
LibrarySystem_Init
  LibrarySystem
——————————————————————
  borrowed = ∅
```

**عملیات: امانت گرفتن کتاب**
```
BorrowBook
  ΔLibrarySystem
  b? : BOOK
  m? : MEMBER
——————————————————————
  b? ∈ stock                          -- پیش‌شرط: کتاب باید موجود باشد
  b? ∉ dom borrowed                   -- پیش‌شرط: کتاب نباید قبلاً امانت رفته باشد
  borrowed' = borrowed ∪ {b? ↦ m?}    -- پس‌شرط: کتاب به لیست امانت اضافه می‌شود
  stock' = stock
```

**عملیات: برگرداندن کتاب**
```
ReturnBook
  ΔLibrarySystem
  b? : BOOK
——————————————————————
  b? ∈ dom borrowed        -- پیش‌شرط: کتاب باید در حال حاضر امانت باشد
  borrowed' = {b?} ⩤ borrowed
  stock' = stock
```

## ۵. ابزارها

### ۵.۱ CZT — Community Z Tools
- افزونه Eclipse که شامل type-checker و ابزار انیمیشن **ZLive** است
- از سایت `czt.sourceforge.net` قابل دریافت است؛ نصب از طریق Eclipse Update Site انجام می‌شود
- کاربرد: بررسی سازگاری نحوی/نوعی مشخصات (فاز ۳) و اجرای نمادین عملیات‌ها بدون نیاز به کدنویسی (فاز ۴)


### ۵.۲ Fuzz (جایگزین سبک برای type-checking)
- یک type-checker سبک و قدیمی برای Z که در برخی دوره‌های دانشگاهی هنوز استفاده می‌شود؛ اگر CZT برای محیط سنگین بود می‌تواند گزینه پشتیبان باشد

## ۶. جمع‌بندی کارهای مرتبط (از دید نوشتن Z)

مرور این سه مرجع:

- **CoCon (Kanav و همکاران، ۲۰۱۴):** هسته یک سامانه مدیریت کنفرانس با تمرکز بر محرمانگی اسناد در ابزار HOL/Isabelle راستی‌آزمایی شده است. نکته قابل استفاده: نحوه‌ی جدا کردن قیدهای مربوط به محرمانگی/دسترسی از بقیه منطق سیستم.
- **Nagoya و Liu (۲۰۱۵):** با متدولوژی سه‌مرحله‌ای «توصیف صوری → طراحی → پیاده‌سازی» نشان دادند این رویکرد خطاهای مرحله اجرا را کاهش می‌دهد — همان الگویی که در فاز ۶ پروژه (توسعه مدل‌محور) دنبال می‌شود.
- **Abdallah و Khayat (۲۰۰۶):** چند مدل کنترل دسترسی مبتنی بر نقش (RBAC) را با Z مشخصه‌سازی کرده‌اند. این مستقیماً به نیاز شما برای تعریف دقیق سطوح دسترسی نویسنده/داور/مدیر مرتبط است.
